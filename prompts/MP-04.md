# MP-04 — Mission Planner: stato bozza spedizione

> Piano: `plans/PLAN-018-mission-planner.md` v3 §T-004. Engine: MP-01.
> Master: `prompts/PLAN-018-mission-planner.md`. blocked_by: **MP-01**.

## Goal

Lo stato della bozza di spedizione del pannello "Planner": cosa parte, con cosa, calcolato come **funzione pura dello stato live di dominio**.

## Deliverable

- **Context locale** al pannello (è stato UI di bozza, non dominio — invariante state-management):
  - `draft = { assignments: slotId → residentId, loadout: residentId → {slot→itemId}, consumables: itemId → qty }`;
  - **recompute da stato live**: ad ogni render/cambio, la preview risolve residente+item dallo stato di dominio corrente — se un residente cambia stato mentre il pannello è aperto (partito, ferito, rimosso), la bozza mostra l'invalidazione (warning + `canEmbark` false), mai numeri stale;
  - `canEmbark`: slot obbligatori vuoti, residente invalido, item non più disponibile → blocco dichiarato.
- **Delta**: snapshot dell'output canonico precedente (da `serializeOutcome` di MP-01) → delta per metrica; primo render = nessun delta.
- **Undo** (ultimo cambio) e **Reset to baseline** (bozza iniziale all'apertura) — i pattern UI concordati in MP-05 si appoggiano a queste primitive.
- **Contratto di lancio**: `buildLaunchPayload(draft, live)` → payload tipizzato `{questId, party:[{residentId, slotId, loadout}], consumables}`; validazione atomica (tutto valido o niente); rollback definito se l'avvio quest fallisce.
- Bozza **non persiste** alla chiusura (default v23); nessuna scrittura su `PersistenceService` in questo task.
- Telemetry hooks pronti (`mission_planner_draft_change`) senza chiamate ancora (le fa MP-05).

## Acceptance

- Test: palindromo bozza → outcome identico via `serializeOutcome`; invalidazione quando lo stato live cambia; payload di lancio rifiutato con motivo se bozza invalida.
