# ADR001-T3 — Migrate ActivityDefinition → C2 config schema

## Context
Part of Quest Engine Reconciliation (ADR-001). Phase T3 migrates the existing `ActivityDefinition` runtime to a config-driven C2 schema, enabling data-driven quest/activity definitions instead of hardcoded runtime objects.

## Objectives
- Migrate existing `ActivityDefinition` runtime to Zod-based C2 config schema
- Update `defaultConfig.ts` to include activity definitions
- Ensure backward compatibility with existing quest/activity data
- Add unit tests for schema validation and migration

## Scope

### Files to Create
- `src/balancing/config/idleVillage/activityDefinitions.ts` — Zod schema for C2 activity definitions
- `tests/unit/idleVillage/activityDefinitions.test.ts` — Schema validation tests

### Files to Modify
- `src/balancing/config/idleVillage/defaultConfig.ts` — Add activity definitions to default config
- (No runtime engine changes in this phase — schema migration only)

### Out of Scope
- Runtime engine changes (deferred to T4)
- Quest engine integration (deferred to T6)
- UI component updates (deferred to T5)

## Guardrails

### Invariants
- **Config-first**: All activity definitions must be in Zod schema, not hardcoded runtime
- **Persistence**: Use `PersistenceService` for any state (though this phase is schema-only)
- **i18n**: Any user-facing strings must use `idleVillage` namespace
- **No standalone CSS**: Skin tokens only (not applicable to this schema phase)

### Constraints
- Schema must validate existing activity data without breaking changes
- Migration must be additive — do not delete existing definitions until T4
- Tests must cover all activity definition types

## Implementation Plan

### Step 1: Define C2 Activity Schema
Create Zod schema in `activityDefinitions.ts`:
- `ActivityDefinitionSchema` — base schema with id, name, description, type
- `QuestActivitySchema` — extends base with quest-specific fields (reward, risk, duration)
- `CurioActivitySchema` — extends base with curio-specific fields (lore, flavor)
- Validation helpers for runtime checks

### Step 2: Migrate Existing Definitions
Extract existing activity definitions from runtime:
- Convert hardcoded definitions to config objects
- Preserve all existing fields and values
- Add to `defaultConfig.ts` under `activityDefinitions` key

### Step 3: Add Unit Tests
Create comprehensive tests in `activityDefinitions.test.ts`:
- Schema validation tests (valid/invalid inputs)
- Migration correctness tests (compare old vs new)
- Edge case tests (missing fields, optional fields)

### Step 4: Verify Backward Compatibility
- Ensure existing quest/activity data still loads
- Validate schema against current activity data
- No runtime errors in existing quest engine
