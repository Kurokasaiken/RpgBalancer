# ADR001-T6 — Quest telemetry + outcome parity tests

## Context
Part of Quest Engine Reconciliation (ADR-001). Phase T6 adds telemetry tracking for quest events and creates outcome parity tests to verify that the new C2 quest engine produces identical results to the old C1 runtime.

## Objectives
- Add telemetry tracking for quest events (start, complete, fail, outcome)
- Create outcome parity tests comparing C1 vs C2 quest engine
- Verify that quest outcomes are deterministic and reproducible
- Ensure telemetry events are properly validated

## Scope

### Files to Create
- `src/analytics/idleVillage/questTelemetry.ts` — Telemetry event definitions and helpers
- `tests/unit/idleVillage/questOutcomeParity.test.ts` — Parity tests comparing C1 vs C2

### Files to Modify
- (No direct engine modifications — telemetry is additive)

### Out of Scope
- Deprecating C1 runtime (deferred to T7)
- Trusted doc updates (deferred to T8)
- UI component updates (deferred to T5)

## Guardrails

### Invariants
- **Config-first**: Telemetry event schemas must use Zod validation
- **Persistence**: Telemetry must use existing analytics infrastructure
- **i18n**: Any user-facing strings must use `idleVillage` namespace
- **No standalone CSS**: Skin tokens only (not applicable to this phase)

### Constraints
- Telemetry must not impact quest engine performance
- Parity tests must cover all quest event types
- Telemetry events must be validated against schema

## Implementation Plan

### Step 1: Define Telemetry Events
Create `questTelemetry.ts` with:
- Zod schemas for quest events (start, complete, fail, outcome)
- Helper functions to emit telemetry events
- Integration with existing analytics infrastructure

### Step 2: Add Telemetry to Quest Engine
Hook telemetry into quest engine:
- Emit `quest_start` event when quest begins
- Emit `quest_complete` event when quest succeeds
- Emit `quest_fail` event when quest fails
- Emit `quest_outcome` event with outcome details

### Step 3: Create Parity Tests
Create `questOutcomeParity.test.ts` with:
- Test cases for each quest event type
- Comparison of C1 vs C2 outcomes with same seed
- Validation that outcomes are identical
- Edge case tests (failures, edge conditions)

### Step 4: Verify Telemetry
- Run telemetry events through validation
- Ensure events are properly formatted
- Check for performance impact
