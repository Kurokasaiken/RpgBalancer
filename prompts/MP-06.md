# MP-06 — Mission Planner: integrazione pagina quest + risoluzione modello A

## Goal

Collegare il Planner alla quest e portare la risoluzione sullo **stesso modello** del Planner: stesso modello, stesse funzioni pure, stessi input — il resolver **campiona dalla distribuzione** che il Planner mostra (non produce "lo stesso numero").

## Deliverable

1. **UI hook**: pulsante "Planner" nella quest detail (`/poi-quest-detail-roster-time-clock`), pre-partenza. Il lancio usa il percorso di avvio esistente + payload di MP-04 (`buildLaunchPayload`); validazione lato dominio.
2. **Resolver per-residente** (estensione di `resolveMilestoneWithoutAnimation` o nuova funzione accanto):
   - tiri rischio **per residente** presente in `S` (non un tiro party);
   - il **morto** esce da `S` per le fasi successive (le sue stat escono da `buildAstrolabeSkillsForPhase`); il **ferito resta** e continua a tirare;
   - stato per-membro `alive|injured|dead` persistito lungo le fasi della quest (nuovo stato di dominio nel loop di risoluzione — decidere forma minima e documentarla);
   - **checkpoint continua/ritirati dopo ogni fase** (D2, deciso): la superficie quest offre al giocatore la scelta continua/ritirati; ritiro → tier calcolato sulle fasi giocate (regola ≥50%), effetti delle fasi risolte già applicati;
   - **wipe** (S=∅): chiusura forzata → tier `deadly`;
   - `isPassingVerdict` → `bigwin | win` (**`almost` non passa più** — cambia `resolveQuestOutcomeTier`; changelog nel codice + test aggiornati).
3. **`resolvePartyConsequences`**: inventario call-site (`grep -rn resolvePartyConsequences src/`), rimozione dal flusso quest (mark `deprecated` + migrazione consumer documentata); reward/effects a fine quest invariati salvo la parte ferita/morte.
4. **Accordo statistico**: test seeded — per fixture fisse, la distribuzione campionata dal resolver per-residente concorda con la DP entro **±1.5pp** (10k tiri); il test è secondario, il contratto resta la spec.
5. Consumabili del payload: applicati a ogni check (`applyConsumableRiskEffects`), **consumati al lancio**; equip: stat effettive via `applyLoadoutToResident` (stessa funzione di MP-03).

- Regressione: le quest avviate senza Planner seguono lo stesso nuovo modello; test esistenti aggiornati dove la semantica è cambiata (elencarli nell'evidence).
