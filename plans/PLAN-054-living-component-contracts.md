### 2.2 Il Living Sync Gate (Valutazione su `BASE..WT` in `contractsCheck.ts`)

1. **Pass Globale Ratchet (sempre eseguito su `BASE..WT`, anche se nessun `scope_files` componente è toccato):**
   - Verifica che `manifest.base_sha === sealed_base_sha` (da `.mw/trusted.lock.json` / `plan:stamp open`).
   - Verifica il Ratchet strutturale YAML su tutti i file `.mw/contracts/**` e il Ratchet delle asserzioni su tutti i blocchi `// INV:<id>` nei file di test rispetto a `BASE`. Qualsiasi indebolimento in un commit di soli test senza `Mode B-amend` autorizzato fallisce immediatamente. **Il pass globale è solo statico** (insiemi YAML parsati + estrazione AST): non esegue check runtime — i check scattano solo per intersezione con il trigger set esteso del Pass Per-Componente (sotto), quindi un commit di soli test/snapshot non viola il budget ≤90s perché esegue solo i test `INV` mirati, non suite intere.
2. **Pass Per-Componente (trigger set esteso):** per ogni componente `C`, il pass scatta quando `git diff -M40% BASE` interseca `C.scope_files` **oppure un file di test che ospita un blocco `// INV:<id>` di `C` (toccato o appena taggato) oppure l'import-closure di quel blocco** (helper/fixture). In quest'ultimo caso il gate esegue **solo i test `INV` mirati** (`vitest run <file> -t <id>`; per i blocchi `INV` in suite Playwright, i file di test sono negli `e2e_trigger_globs` del check e nella sua cache key) e valuta l'`executedCount` — così un diff di soli test che rende un'asserzione irraggiungibile fallisce, non solo quello che tocca `scope_files`. Il run mirato ha un **budget secondario ≤90s combinato per task**: se un edit a un helper condiviso gonfia il trigger set oltre budget, il gate scala a **una full-file run batch** dei file affetti (un processo, `--testNamePattern` per intersezione `INV`). Regola targeted-vs-full: il `-t` mirato è il default del sync gate, ma ogni `INV` toccato deve risultare `passed` anche nella **full-file run a chiusura** (`verify:bundle`), così stato condiviso in `describe`/`beforeAll` non produce uno split "sync green, closure red".

Oltre `N` amend/retire **per intervallo `BASE..WT`** (default 3, configurabile; contato per `INV-id` distinto — `red:retire` + amend sullo stesso `INV` contano una sola volta; il boundary `trusted:seal` è il boundary del contatore) serve approvazione esplicita del Director — registrata solo via canale Director (`.mw/mapping-approvals.jsonl` non è emettibile da comandi agent-callable). ## 5. Appendice — Note di esecuzione non bloccanti (DeepSeek, acceptance round 9)

Raffinamenti registrati nel dibattito come "for the execution log": non modificano la semantica del gate accettata in r009, ma devono guidare l'implementazione.

1. **Baseline capture fuori budget:** la cattura baseline (worktree a `base_sha` + run) è esente dal budget ≤90s del sync gate per costruzione; è one-shot per `INV`, il risultato è **cacheato in `.mw/trusted.lock.json`** dopo la cattura e loggato nel Decision Report come "baseline established; future closures use sealed count".
2. **Baseline su closure `BASE`, non `WT`:** la cattura gira in un worktree pulito a `base_sha`, quindi usa l'intera dependency-closure a `BASE` (non quella `WT`) — confronto mele-con-mele garantito.
3. **`unknown` da seal non-sync:** se un seal successivo non-`SYNC_GATE=1` produce `executedCount` `unknown` per `INV` Playwright già noti, il gate **ricade sul conteggio del più recente seal `SYNC_GATE=1`** per lo stesso `INV` invece di forzare una nuova cattura.
4. **Full-file check su `WT` corrente:** il requisito "`INV` toccato `passed` nella full-file run" è valutato sul report della run `WT` corrente in `closureLint.ts`, non sull'ultimo `verify:bundle` storico.
5. **Caso 13 parametrizzato:** il caso dependency-closure/`SKIPPED_CACHE` è parametrizzato su `{skipped, failed, passed}` × `{dependency-changed, unchanged}` asserendo il motivo di fallimento distinto ("check failed" ≠ "check not executed").
6. **`expect.poll` dentro `test.each`:** sub-caso del caso 14 — il conteggio è **per-istanza di test**, non per-tabella; l'estrattore deve preservare la distinzione.
7. **`executed_count_status` stabile nel Decision Report:** campo schema `not_applicable_new | not_applicable_unknown_baseline | enforced` (non testo libero), così `closureLint.ts` può verificare che ogni `INV` affetto abbia esattamente uno dei tre stati — l'esenzione diventa auditabile, non narrativa.
